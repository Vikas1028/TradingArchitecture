NEWS EVENT TRADING SERVICE - DETAILED ARCHITECTURE AND FLOW
===============================================================

Purpose
-------
This document defines a detailed architecture for a stock-news/event-based trading service.
The service will fetch stock-related news and structured corporate events from the internet,
classify them, map them to stocks, score their likely impact, combine them with live market
reaction, and generate trading alerts/signals.

This system is designed for:
- Dividend-related event detection
- Quarterly result-related event detection
- Incident / breaking-news event detection
- Event-based watchlists
- Paper trading
- Future integration with real trading

This architecture is designed so it can be built primarily in Go.

-------------------------------------------------------------------------------
1. HIGH-LEVEL OBJECTIVE
-------------------------------------------------------------------------------

Build a system that does the following:

1. Fetch stock-related news and official corporate events from multiple sources
2. Normalize all data into one internal structure
3. Detect what kind of event it is
4. Map the event to a listed stock symbol
5. Measure how important the event is
6. Check whether the market is reacting strongly
7. Generate alerts and trade candidates
8. Optionally execute paper trades or live trades

Important principle:
Do NOT trade directly from raw headlines.
Trade only when:
- event is reliable
- event is relevant
- stock mapping is correct
- price reaction confirms the event
- your setup conditions match

-------------------------------------------------------------------------------
2. CAN THIS SERVICE BE WRITTEN IN GO?
-------------------------------------------------------------------------------

Yes.

This service can absolutely be built in Go.

Go is well-suited for:
- concurrent HTTP polling
- API integrations
- schedulers/workers
- Kafka producers/consumers
- JSON handling
- low-latency processing
- rule-based event classification
- signal generation
- alerting systems
- REST APIs
- event pipelines
- scalable microservices

Where Go is weaker:
- advanced NLP
- messy HTML scraping compared to Python ecosystem
- LLM-heavy pipelines
- complex PDF extraction

Recommended engineering decision:
- Build version 1 fully in Go
- If later needed, add Python only for advanced NLP or PDF parsing

-------------------------------------------------------------------------------
3. BUSINESS PROBLEM THIS SERVICE SOLVES
-------------------------------------------------------------------------------

This application solves the problem of converting market-relevant information into
structured, tradeable signals.

Examples:
- Dividend declared -> track yield surprise, ex-date relevance, reaction
- Quarterly results announced -> detect result event, measure surprise, confirm with price
- Negative incident -> detect event, link it to stock, short only if price confirms
- Sudden event like "stock down by 20%" -> identify if news and price anomaly align

Without such a service:
- you manually monitor many pages and apps
- you miss events
- you react late
- you confuse rumors with real events
- you have no consistent structure for event-based trading

-------------------------------------------------------------------------------
6. KEY PRINCIPLE: PRICE CONFIRMATION IS MANDATORY
-------------------------------------------------------------------------------

This is not optional.

A headline by itself is not a trade.

Example:
- Good result but stock falls -> expectations were higher
- Bad result but stock rises -> bad news already priced in
- Negative article appears after price already dropped -> late entry risk
- Rumor spreads -> no reliable confirmation

Therefore, every event must be evaluated with:
- source reliability
- duplication count across sources
- time freshness
- market reaction
- volume expansion
- technical confirmation

8. DETAILED SERVICE DEFINITIONS
-------------------------------------------------------------------------------

8.1 news-collector
------------------
Responsibility:
Fetch raw items from all configured sources.

Inputs:
- source configs
- polling schedules
- API keys / cookies / auth if required

Outputs:
- raw news item events to Kafka
- raw items stored in DB if needed

Submodules:
- nse collector
- bse collector
- external news collector
- scheduler
- deduplicator

Key tasks:
- call source endpoints
- parse response
- capture publish time
- capture URL
- store raw text
- generate dedup hash
- publish to topic news.raw

8.2 news-normalizer
-------------------
Responsibility:
Convert source-specific payloads into one internal structure.

Inputs:
- news.raw topic

Outputs:
- normalized events to news.normalized

Tasks:
- unify timestamp format
- clean titles
- clean summaries
- standardize fields
- strip HTML noise
- map source to common source_type
- preserve metadata

8.3 event-classifier
--------------------
Responsibility:
Classify normalized content into event types.

Inputs:
- news.normalized

Outputs:
- news.classified

Tasks:
- keyword/rule classification
- positive / negative / neutral
- severity score
- confidence score
- event-type selection
- actionability decision

Version 1 approach:
- use rule-based keyword maps
- use phrase patterns
- use source priority

Later:
- optionally add ML or LLM classifier

8.4 symbol-mapper
-----------------
Responsibility:
Map event/company mention to tradable stock symbol.

Inputs:
- news.classified
- symbol master DB

Outputs:
- mapped stock event

Tasks:
- map company full name
- map short name
- map aliases
- map ticker symbols
- resolve ambiguity
- attach company_name + symbol

Example:
"HDFC Bank Ltd", "HDFC Bank", "HDFCBANK" -> HDFCBANK

8.5 market-reaction-engine
--------------------------
Responsibility:
Measure price and volume reaction after an event.

Inputs:
- event stream
- live tick/candle stream
- price store / candle store

Outputs:
- event reaction snapshot

Tasks:
- compute 1m / 5m / 15m returns
- compare to index
- compute volume ratio
- compute gap from previous close
- compute VWAP distance
- compute anomaly score
- check structure break
- decide if market confirms event

8.6 scoring-engine
------------------
Responsibility:
Combine event quality and market reaction into a weighted score.

Inputs:
- classified event
- reaction snapshot

Outputs:
- event score

Possible dimensions:
- source reliability
- event severity
- confidence
- sentiment strength
- duplication count
- freshness
- price confirmation
- volume confirmation

8.7 signal-engine
-----------------
Responsibility:
Convert scored events into trade ideas.

Possible outputs:
- IGNORE
- WATCH
- LONG_CANDIDATE
- SHORT_CANDIDATE
- TRIGGER_LONG
- TRIGGER_SHORT

Tasks:
- apply strategy rules
- generate entry logic
- assign risk template
- create trade candidate event

8.8 alert-service
-----------------
Responsibility:
Send actionable alerts.

Channels:
- Telegram
- dashboard
- email
- Slack
- mobile notification

Alert example:
Symbol: ABC
Event: RESULT_DECLARED
Bias: LONG_CANDIDATE
Score: 82
Reason: Strong result + volume breakout + price above VWAP

8.9 dashboard-api
-----------------
Responsibility:
Provide dashboards and query APIs for:
- latest events
- symbol-wise event history
- event score list
- signal list
- reaction metrics
- audit trail

8.10 paper-trade-engine
-----------------------
Responsibility:
Simulate trade execution for backtesting / forward testing.

8.11 live-trade-engine
----------------------
Responsibility:
Place real orders.
This should be the final step, not the first.

-------------------------------------------------------------------------------
9. END-TO-END FLOW
-------------------------------------------------------------------------------

9.1 Master flow
---------------
1. Source fetcher reads latest updates from official sources and news APIs
2. Raw item is published to Kafka topic news.raw
3. Normalizer converts it to standard structure
4. Classifier identifies event type and severity
5. Symbol mapper links it to correct stock
6. Storage persists it in DB
7. Reaction engine checks live market response
8. Scoring engine combines event + reaction
9. Signal engine decides long / short / ignore / watch
10. Alert service sends notification
11. Optional paper trade or live trade occurs

-------------------------------------------------------------------------------
10. DETAILED FLOW BY EVENT TYPE
-------------------------------------------------------------------------------

10.1 Dividend flow
------------------
1. collector fetches corporate action / board meeting updates
2. event says company will consider dividend
3. classifier marks DIVIDEND_NOTICE
4. mapper links event to symbol
5. storage stores notice
6. later, official declaration arrives
7. classifier marks DIVIDEND_DECLARED
8. metadata includes dividend amount and type
9. yield calculator compares dividend to current stock price
10. reaction engine checks price behavior
11. signal engine decides:
   - ignore
   - watch
   - long candidate

Important logic:
- special dividend is usually more impactful than routine dividend
- very low yield dividend may not matter
- ex-date behavior differs from declaration-day behavior

10.2 Quarterly result flow
--------------------------
1. collector fetches board meeting notice for results
2. classifier marks RESULT_MEETING_NOTICE
3. system stores expected result date
4. result filing is released
5. classifier marks RESULT_DECLARED
6. if text parsing available, extract profit/revenue/margin terms
7. reaction engine watches first 1m / 5m / 15m market response
8. scoring engine measures confidence + price confirmation
9. signal engine decides long candidate / short candidate / ignore

Important logic:
- actual price reaction matters more than headline optimism
- results may be "good" but stock may still fall
- entry should come from structure, not emotion

10.3 Incident flow
------------------
1. external news source publishes breaking item
2. collector receives article
3. classifier detects incident type
4. symbol mapper links company to stock
5. reaction engine checks sudden move
6. if price + volume confirm, score increases
7. signal engine generates watch/short/long depending on event nature

Example:
- fire in plant
- stock down sharply
- volume surge
- no positive clarification
=> SHORT_CANDIDATE or WATCH_SHORT_BELOW_VWAP

17. STRATEGY LOGIC EXAMPLES
-------------------------------------------------------------------------------

17.1 Dividend strategy
----------------------
Possible logic:
- only consider official declarations
- special dividend preferred over routine small dividend
- ignore low-yield/no-surprise dividend
- require price strength above VWAP after event
- trade only if there is intraday structure confirmation

17.2 Quarterly result strategy
------------------------------
Possible logic:
- event must be official
- result should show strong market response
- trade breakout above first 5m/15m structure for positive event
- trade breakdown below first 5m/15m structure for negative event
- avoid if move is already exhausted

17.3 Incident short strategy
----------------------------
Possible logic:
- negative incident severity high
- trusted or repeated sources
- stock below VWAP
- price breaks intraday support
- no quick reversal after event
- avoid if near lower circuit / illiquid / spread too wide

18. TIME SCHEDULING DESIGN
-------------------------------------------------------------------------------

Not all sources need same frequency.

Recommended polling intervals:

Fast:
- external breaking-news APIs: every 10 to 30 seconds

Medium:
- exchange announcements during market hours: every 30 to 60 seconds

Slow:
- dividend schedules / event calendars: every 5 to 15 minutes

Very slow:
- static metadata refresh: every few hours or daily

Important:
Do not hammer every endpoint every second.
That is wasteful and may get you blocked.

-------------------------------------------------------------------------------
19. DEDUPLICATION DESIGN
-------------------------------------------------------------------------------

Deduplication is critical.

Problems without dedup:
- same article from multiple fetch cycles
- same filing updated repeatedly
- duplicated alerts
- repeated signals

Dedup keys:
- source + external_id
- normalized title hash
- title + published_at hash
- url hash

Recommended recent dedup storage:
- Redis for short-term
- DB for long-term audit

- event dashboards
- historical study support

Goal:
Convert events into filtered trade candidates.

Phase 4 - Paper trading
-----------------------
Add:
- entry logic
- simulated trades
- signal outcome tracking
- daily review reports

Goal:
Measure whether strategy works.

Phase 5 - Live trading
----------------------
Add:
- broker execution integration
- risk controls
- kill switch
- order monitoring

-------------------------------------------------------------------------------
30. WHY THIS ORDER MATTERS
-------------------------------------------------------------------------------

Wrong order:
- build auto-trading first
- then figure out if event quality is good
- then realize source mapping and reaction logic are weak
- lose money

Correct order:
1. collect
2. normalize
3. classify
4. map
5. react
6. score
7. alert
8. paper trade
9. live trade

This is the sane path.

-------------------------------------------------------------------------------
31. RISKS AND CHALLENGES
-------------------------------------------------------------------------------

Main technical risks:
- source instability
- anti-bot protections
- HTML changes in websites
- duplicate content
- incorrect symbol mapping
- late news
- low-quality news sources
- overfitting event rules
- false positives
- market reaction happening before your fetch time
- too many noisy alerts

Main trading risks:
- event already priced in
- wrong interpretation of headline
- price reversal after initial move
- illiquid names
- circuit risk
- fake/rumor articles
- expectation mismatch during results

-------------------------------------------------------------------------------
32. WHAT MAKES THIS SYSTEM USEFUL
-------------------------------------------------------------------------------

This system becomes genuinely useful when it can answer:

- What just happened?
- Is it official or rumor-based?
- Which stock is affected?
- Is it positive or negative?
- How severe is it?
- Is the stock actually reacting?
- Is the move strong enough to trade?
- Should I ignore, watch, or trade?

If it cannot answer these properly, it is just a noisy news scraper.

33. FINAL RECOMMENDATION
-------------------------------------------------------------------------------

Build version 1 in Go.

Do not overcomplicate it with AI from day one.

Start with:
- official dividend and result events
- strong normalization
- clean symbol mapping
- market reaction confirmation
- alerts only

Then add:
- incident detection
- scoring
- paper trading
- real trading

The edge is not in collecting headlines.
The edge is in structured event detection plus reaction confirmation plus disciplined rules.
